# V2 — Fundação da aplicação

A V2 evolui o bootstrap da V1 para uma fundação headless de aplicação, com settings por ambiente, primitives compartilhadas de persistência, conta técnica, pessoa natural e endereços.

## Stack

- Python 3.13.x;
- Django 5.2.x LTS;
- Django REST Framework 3.16.x;
- PostgreSQL 17.x;
- Redis 8.x;
- uv e `uv.lock`;
- Docker Compose para PostgreSQL e Redis.

## Implementado

- settings `base`, `local`, `test` e `production`;
- DRF headless, somente JSON e sem autenticação HTTP implícita;
- `TimeStampedModel`, `ActorStampedModel`, `SoftDeleteModel` e `BaseModel`;
- QuerySet e managers próprios para soft delete;
- `accounts.User` baseado em `AbstractUser`, com login por username e senha;
- separação entre conta técnica e `people.NaturalPerson`;
- `Country`, `State` e `City` com FKs protegidas e constraints contextuais;
- `BaseAddress` abstrata e `NaturalPersonAddress` concreta;
- propriedade calculada `full_address`;
- migrations iniciais versionadas;
- testes unitários, de integração e de inicialização.

## Decisões arquiteturais

- Django Admin, templates, messages, staticfiles e sessões não são habilitados.
- O User não armazena nome civil e não herda de `BaseModel`.
- `NaturalPerson` referencia o User por `OneToOneField` protegido; um User pode existir sem pessoa.
- `NaturalPersonAddress` usa `ForeignKey`, permitindo vários endereços por pessoa.
- Endereços usam soft delete; catálogos geográficos não usam, evitando localidades ocultas ainda referenciadas.
- Exclusão física da pessoa executa cascade dos endereços; soft delete não executa cascade lógico.
- Idade e endereço completo são calculados, não persistidos.
- Não existem abstrações genéricas de repository, service, ViewSet ou CRUD.

## Limitações conhecidas

- soft delete não possui cascade lógico automático;
- registros logicamente excluídos continuam ocupando constraints únicas;
- `on_delete` é aplicado somente em exclusões físicas;
- `created_by` e `updated_by` são identificação simples, não auditoria completa;
- o banco permite uma pessoa sem endereço; uma quantidade mínima deverá ser validada em um fluxo futuro;
- os catálogos geográficos começam vazios e devem ser preenchidos pelo projeto consumidor;
- não existe endpoint HTTP de login ou emissão de token.

## Fora do escopo

- JWT e endpoints de autenticação;
- serializers e ViewSets;
- OpenAPI e CORS;
- padrão global de erros;
- Celery e integração do Redis;
- CI/CD;
- Docker da aplicação Django;
- abstrações genéricas de serviço ou repositório.

## Validação

A V2 foi validada com banco PostgreSQL recriado desde o zero:

```bash
uv sync --locked
docker compose up -d --wait
uv run python manage.py migrate
make check-settings
make test
make startup-test
```

Resultado do congelamento:

- 38 testes passando;
- settings local, test e production sem problemas;
- WSGI e ASGI carregando os settings de produção;
- migrations de `accounts`, `people` e `addresses` aplicadas;
- `createsuperuser` e autenticação por username/senha validados;
- PostgreSQL e Redis healthy;
- persistência confirmada após reiniciar os containers;
- nenhuma migration pendente.
